# ADR 0004 — Windows Credential Manager backend

**Status:** Accepted for Issue #11 implementation  
**Date:** 2026-10-30

## Context

credentials-d needs a native persistent credential store on Windows without
placing secrets in application settings or introducing an application-managed
vault by default.

Windows Credential Manager exposes generic credentials through the WinCred API.
Generic credential blobs are application-defined and are protected by the
current Windows user's credential store.

The common credentials-d contract already requires:

- explicit application namespaces;
- opaque non-secret handles;
- scoped plaintext access;
- no silent fallback;
- honest capability reporting;
- OS-CSPRNG record identifiers.

## Decision

The Windows backend is an explicit DUB subpackage:

```text
credentials-d:windows
```

The root credentials-d package does not automatically import or select it.

### Native API

The backend uses only:

- `CredWriteW`;
- `CredReadW`;
- `CredDeleteW`;
- `CredGetSessionTypes`;
- `CredFree`.

A narrow local FFI declaration is preferred over a large third-party Windows
binding dependency.

### Credential type and persistence

Records use `CRED_TYPE_GENERIC`.

The backend requests `CRED_PERSIST_LOCAL_MACHINE`, which preserves a
credential for later sessions of the same Windows user on the same machine
without requesting enterprise/roaming persistence.

Before writes, `CredGetSessionTypes` is used to establish that local-machine
persistence is available for generic credentials. If it is not, the backend
reports `unavailable`; it does not downgrade persistence.

### Record identity

Each new record receives a 128-bit locator generated by the qualified OS CSPRNG
primitive.

The native target name is derived only from:

- a fixed credentials-d prefix;
- the validated application namespace;
- backend/version marker;
- the opaque random locator.

No profile name, OSM display name, email address, OAuth scope or credential
plaintext is placed in WinCred metadata.

The public handle remains non-secret.

### Blob limit

Windows generic credential blobs are bounded by
`CRED_MAX_CREDENTIAL_BLOB_SIZE` (2560 bytes).

The backend validates the length before entering WinCred and reports
`tooLarge` rather than relying on a native failure.

### Store semantics

`CredWriteW` has update semantics and provides no create-only primitive.

For `store`, the backend therefore probes the randomly generated target before
writing. A cryptographically random 128-bit locator makes accidental collision
negligible, but the probe/write pair is not an atomic cross-process
create-if-absent transaction.

The implementation does not claim otherwise.

For `replace`, the existing target is probed first so a missing record returns
`notFound` instead of being silently created by `CredWriteW`.

### Read lifetime

`CredReadW` allocates one native credential block containing the plaintext
blob.

The backend:

1. validates the returned structure;
2. exposes the blob only through the scoped `SecretVisitor`;
3. overwrites the blob using `core.volatile.volatileStore`;
4. calls `CredFree`.

This does not erase copies created by Windows internally or deliberately by the
consumer.

### Concurrency

Operations are serialized per `WindowsCredentialStore` instance.

This is a conservative backend contract while cross-thread/cross-process
behavior is not independently qualified. It is not a transaction guarantee
across distinct processes or store instances.

### Security claims

The backend reports:

- persistent: yes;
- protection: native user credential store;
- unlock: OS-managed;
- mobility: local device;
- user presence: no;
- blocking: may block;
- concurrency: serialized;
- logical deletion confirmation: yes.

It does **not** claim:

- hardware-backed protection;
- Windows Credential Guard protection for generic credentials;
- per-Dunia-profile cryptographic separation;
- physical secure deletion from backups/snapshots;
- protection against the current Windows user running hostile code.

### Failure behavior

No Windows backend error causes an automatic fallback.

Relevant native conditions are mapped into the common non-secret status model,
including:

- missing record;
- unavailable logon credential service;
- permission denial;
- invalid/backend failure.

Native error messages containing arbitrary data are not included in public
status values.

## Consequences

The Windows backend can be used independently of Linux/macOS native libraries.

Dunia or another consumer explicitly opts into `credentials-d:windows`.

A future stronger Windows backend may use a different Windows protection
mechanism, but it must be a distinct explicit backend or a separately accepted
contract change rather than a silent substitution.

## Verification

Production qualification requires:

- DMD 2.111.0 and LDC 1.41.0 native Windows builds;
- real ephemeral Windows Credential Manager integration tests;
- persistent reopen/read through a fresh backend instance;
- replace behavior;
- deletion behavior;
- wrong-namespace rejection;
- oversize rejection before native write;
- cleanup of test records on every normal integration path.
